여러 대의 리눅스 센서가 각자 관측한 트래픽은 따로 보면 평범합니다. 하지만 겹쳐 보면, 반복되는 하나의 패턴 — DDoS 봇넷 C2 후보 — 이 드러납니다. C2Hunter는 그 패턴을 찾아내고, 근거와 함께 설명하는 방어 전용 플랫폼입니다.

문제

왜 단일 센서로는 부족한가

정교한 DDoS 봇넷의 C2 통신은 한 지점에서만 보면 그저 흔한 HTTPS 아웃바운드 연결처럼 보이도록 설계됩니다. 주기, 크기, 목적지 어느 것도 그 자체로는 이상하지 않습니다.

하지만 같은 시간대에 여러 대의 내부 호스트가 서로 다른 네트워크 구간에서 같은 목적지를 향해 같은 리듬으로 통신한다면 얘기가 달라집니다. C2Hunter는 이 상관관계를 드러내기 위해, 여러 리눅스 센서의 관측을 한 곳으로 모아 비교합니다.

제어 평면과 데이터 평면을 분리한다

Sensor는 항상 Controller 방향으로만 연결을 시작합니다. 흐름(flow) 저장소, 객체(PCAP) 저장소, 큐는 의도적으로 분리되어 있어, 한 계층의 장애가 전체로 번지지 않습니다.

Sensor 설치는 전용 non-root 사용자로 동작하며, 바이너리에는 CAP_NET_RAW / CAP_NET_ADMIN만 부여됩니다. 각 인터페이스는 독립된 AF_PACKET→Flow→spool→upload 파이프라인을 가지므로, 하나의 인터페이스 장애가 다른 인터페이스를 멈추지 않습니다.

모든 evidence는 유형별 점수 상한 안에서만 합산됩니다. 하나의 신호가 전체 점수를 좌우하지 않고, 점수는 항상 근거 목록과 함께 제공됩니다.

≤20
Common Destination
다수의 내부 호스트가 같은 외부 목적지와 통신하는지 확인합니다. 공용 DNS/NTP, 신뢰 CDN 도메인은 자동으로 제외됩니다.
≤25
Non-Well-Known Port
외부 endpoint가 well-known 범위 밖의 service port를 반복적으로 사용하는 패턴을 찾습니다.
≤15
Periodic Beacon
허용된 jitter 범위 안에서 반복되는 주기적 통신 — 간격의 변동계수(CV)를 기준으로 판단합니다.
≤35
Single-Host Composite Beacon
호스트 수가 적어도, 저용량 주기 통신과 안정된 Payload·패킷 크기 패턴을 종합해 판단합니다.
≤80
Analyst Payload Signature
분석가가 승인한 시그니처와 SHA-256 정확 매치되거나, prefix hash·entropy·SimHash 기반 구조 특징이 일치하면 표시합니다.
≤15
Synchronized Communication
여러 호스트가 거의 같은 시각에 반복적으로 동기화된 통신을 하는 패턴을 찾습니다.
≤25
Command → Attack Correlation
작은 inbound 명령 직후, 공통 target에 대한 공격성 트래픽이 증가하는지 시계열로 상관분석합니다.
≤5
Low-Volume Persistence Rarity
저용량 연결이 이례적으로 장기간 안정적으로 지속되는 희소 패턴을 찾습니다.
≤10
Protocol / Payload Similarity
여러 호스트에 걸친 protocol·payload 통계적 특징의 유사도를 결합 지표로 계산합니다.
≤10
Multi-Sensor Context
복수의 독립 센서에서 같은 호스트 패턴이 재현되는지 교차 검증합니다.
≤20

분석가 주도 탐지

사람의 판단을 지우지 않는다

자동 탐지가 놓친 흐름도, 분석가가 직접 검토하고 판정을 남길 수 있습니다. 그 판정은 버전관리되는 시그니처로 이어집니다.

01
최대 256바이트 미리보기
보존된 PCAP에서 직접, 분석가가 명시적으로 요청한 흐름만 미리보기합니다. 그 이상은 노출되지 않습니다.
02
Append-only 검증
C2 또는 BENIGN 판정을 기록합니다. 기존 판정은 수정되지 않고, 이력으로만 쌓입니다.
03
버전관리 시그니처
SHA-256 정확 매치는 고신뢰 경보로, prefix hash·length·entropy·SimHash 구조 매치는 검토 전까지 monitor-only로 표시됩니다.
센서 보안

센서는 최소 권한, 아웃바운드 전용

▸non-root 전용 사용자로 systemd 서비스 실행
▸바이너리에는 CAP_NET_RAW / CAP_NET_ADMIN만 부여
▸모든 연결은 Sensor → Controller 방향으로만 시작
▸설치 시 단 한 번만 노출되는 one-time enrollment token
▸인터페이스별 독립 파이프라인 — 하나가 실패해도 나머지는 계속 동작
▸장애 시 DEGRADED 상태와 인터페이스별 오류 카운터를 보고
정직하게 밝히는 한계

무엇을 할 수 없는지도 압니다

—TLS 페이로드는 복호화하지 않으며, payload 보존은 기본적으로 비활성화되어 있습니다.
—현재 Compose 구성은 단일 호스트 개발 토폴로지이며, production HA 구성이 아닙니다.
—AF_PACKET 가용성과 패킷 드롭률은 호스트 커널·NIC·미러링 품질에 좌우됩니다.
—결정적 브라우저 fixture는 UI 동작만 검증하며, 서버 인가 로직을 검증하지 않습니다.
—PCAP 업로드 원본은 미리보기·추출을 위해 보존되므로, 민감하거나 대용량인 캡처는 보수적인 업로드 한도와 보존 정책이 필요합니다.
